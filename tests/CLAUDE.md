# tests/ — rules for agents writing or changing tests

How the suite is structured and how to write tests for new code. Moved from the repository's
root `CLAUDE.md`, which keeps the rules that bind every contributor and agent in short form and the
PR expectations in full.

## How the suite is structured

- Run `pytest` from the repo root (deps are in `requirements.txt`). The suite is fully offline and finishes in seconds; it runs inside the required `smoke` check on every PR (`.github/workflows/ci.yml`, a job with no API secret exposed), so a failing test blocks merge.
- Tests NEVER call the Anthropic API. Four layers enforce this: pytest-socket (`--disable-socket` in `pyproject.toml`) blocks all network at the socket level; an autouse fixture sets a fake `ANTHROPIC_API_KEY` and resets `shared.api` globals per test; and both backend seams — `shared.api._call_with_retry` and `shared.api._call_claude_code_with_retry` (which would otherwise spawn the Claude Code CLI) — are replaced with functions that raise. The embeddings seam (`shared/embeddings.py`, both providers) gets the identical layered treatment (fake `OPENAI_API_KEY`, globals reset, `_embed_with_retry` blocked).
- To exercise pipeline stages, use the `stub_claude` fixture in `tests/conftest.py` (queue of canned response strings, or a callable dispatcher) — it patches `shared.api.call_claude`, the single chokepoint every module uses. Never let real `anthropic` error types reach the real `_call_with_retry`; tenacity would sleep minutes. For the diversity eval, `stub_embeddings` patches `shared.embeddings.embed_texts` the same way (deterministic per-text vectors, or pass exact geometry).
- All test outputs go to pytest `tmp_path`; the `PIPELINE_OUTPUT_ROOT` env var redirects the `run.py` orchestrators away from the real `outputs/` tree.
- Determinism: an autouse fixture seeds `random`; `sample_language` accepts an injectable `rng`; uuid/timestamp values are asserted by shape, never by value.
- **SDF prompt equivalence** (`tests/test_sdf_prompt_equivalence_and_final_corpus.py`): runs the SDF pipeline end to end on canned replies and compares every request, stage file and the final corpus with recorded files (`tests/fixtures/sdf_prompt_equivalence/`). Any difference fails. A pull request that only refactors must leave the recorded files untouched, so a failure there is a bug. A pull request that changes requests on purpose (a prompt, config or model change) runs `python scripts/regenerate_sdf_prompt_equivalence_recorded_requests.py` and commits the new recorded files in the same pull request, so their diff shows reviewers which requests changed. Nothing else rewrites them. Texts are recorded as sha256 plus length, and each repeated structure is stored once in a table keyed by the path of its first occurrence, so a one-word prompt change rewrites only the hashes it affects. Regenerate only when the pull request is meant to change requests (even if it also touches Python), never to make a failing equivalence test pass, and say in the pull request description that requests change and why. The resume-from-main recordings (`scripts/regenerate_sdf_resume_from_main_recorded_runs.py`) are the exception: they must be made by unmodified `origin/main` code because that is what their test protects, so that script and its test keep their guard.
- **SDF audit equivalence** (`tests/test_sdf_audit_equivalence.py`): runs each model-judged SDF audit (plausibility, shoehorning, variable persistence, compliance, score, `audit_sdf --patterns --principles`, `diversity --ideas`) and the persona check's input builder with canned replies on one run of each on-disk layout, and compares every judge request (and the persona inputs) with recorded files (`tests/fixtures/sdf_audit_equivalence/`). Same rule as the prompt-equivalence test: a pull request that changes judge requests on purpose runs `python scripts/regenerate_sdf_audit_equivalence_recorded_requests.py` and commits the new files in the same pull request; a pull request that only refactors never rewrites them, and nothing regenerates them just to make the test pass.
- **What the per-step tests are for**: requests, stage files, the final corpus, stop messages and call counts of the scenarios in the SDF prompt equivalence recordings (and the audit judge requests in the audit recordings) are pinned there, so the per-layer and per-step SDF tests do not repeat them. They cover what no recording exercises: options no scenario sets, parsing of malformed replies, printed lines, error messages for misuse, pure functions at their boundaries, and one parse happy path, malformed-reply case and zero-call resume per stage. Before adding an SDF test that only checks a request or a stage file on a path a scenario already runs, add the case to a scenario instead.
- Tests encode CURRENT behavior, including known quirks. Don't change pipeline behavior just to make a test expectation nicer — decide the spec first, then flip the test deliberately.

## Writing tests for new code (required for contributions)

Every PR that adds or changes pipeline behavior must add or update tests in the same style — CI runs the suite on every PR, and a stage without tests is a stage that silently breaks at $50 a run. Follow these rules:

- **FIRST**: fast (the whole suite runs in ~1s — keep it that way), independent (no test depends on another's state; `shared.api` globals are reset per test by the autouse fixture), repeatable (seed or inject randomness; assert uuid/timestamps by shape), self-validating (plain asserts, no eyeballing output), timely (written with the change, not after).
- **Test behavior, not implementation**: drive each stage through its public `run()` and assert on returned records, files written, and what reached `call_claude` (the `calls` list from `stub_claude`). Don't reach into private helpers or assert on internal call order unless that IS the contract.
- **Mock only the external boundary**: `stub_claude` stands in for `shared.api.call_claude` — the only external dependency. Real prompt templates, real constitution files, and real (tmp) filesystems stay in play; that's what makes the tests catch template/pipeline drift.
- **Never touch the network or the repo's outputs/**: the API guard and pytest-socket enforce the first; `tmp_path` + `PIPELINE_OUTPUT_ROOT` enforce the second. If a new stage grows a second external dependency, stub it in `tests/conftest.py` the same layered way.
- **Cover the money paths**: every new stage needs at least a parse-happy-path test, a malformed-response fallback test, and a checkpoint/resume test asserting zero API calls for completed work — resume correctness is what protects paid work when a run dies.
- **Derive, don't hardcode, constitution-shaped expectations**: counts and principle ids come from `load_segments()`/`META_PRINCIPLE_IDS`/`_PRINCIPLE_KEYWORDS` (the section count is pinned once, in `test_constitution_loader.py`) — the reading is actively edited and hardcoded ids renumber. FIFO queue stubs are for serial stages only; stages that fan out via `parallel_map` need a callable dispatcher (the stub fails loudly if violated).
- If you change a prompt template's placeholders or add a template, update `tests/test_prompts_render.py` (and the e2e dispatcher markers in `tests/test_e2e_smoke.py` if the opening prose changed).

## How the equivalence recordings work

Only the provider clients (`anthropic.Anthropic`, `openai.OpenAI`) are replaced by fakes that record the keyword arguments they receive and return a canned reply; everything above them (`call_claude`, `_call_with_retry`, `call_openai`) runs for real, so what is recorded is what reaches the wire. Replies are chosen by (stage tag, item id, attempt), never by queue. Recorded files keep long texts as sha256 plus length (a failure prints the new text), store each dealt hand and each repeated large structure once and refer to it by identifier, and normalise only what depends on thread order or the machine (sorted `consideration_scores.jsonl` and failures, `<run directory>` for the absolute path). Name pools come from `FIXED_ENTITY_POOLS_BY_LOCALE`, not Faker. The audit recordings run one worker so request order is deterministic, on a copy of each run cut to a few documents. The audit support module keeps its own minimal copy of the fakes so the two engines can change independently.

The resume-from-main recordings store, per interruption point (`tests/sdf_resume_from_main_interruption_points.py`), the run folder that `origin/main` code leaves when a canned reply source raises `SimulatedProcessCrash` (a `SystemExit`, so no `except Exception` swallows it) as a zip under `tests/fixtures/sdf_resume_from_main/`, without `inputs/` (one shared snapshot zip), `model_calls.jsonl` and `system_prompts/`, with fixed zip dates so the same folder gives the same bytes; and the requests, stage files and final corpus after resuming it on `origin/main`. The test resumes the same folder with the current code and compares in the prompt-equivalence format, leaving checkpoint files out on both sides. The reference is the same interruption resumed on `origin/main`, not an uninterrupted run. The DAD request-settings check works the same way, and also fakes `claude_agent_sdk.query` to record what the `claude_code` and `auto` backends hand the CLI.
